\section*{Задание}

Вариант №123

Доработать приложение из лабораторной работы №1. Существующие CRUD API и key-value-хранилище должны продолжать работать. Добавить CouchDB для постоянного хранения основных объектов.

Предметная область: интернет-магазин.
Основной объект системы: товар.
Документоориентированная система: CouchDB.

\subsection*{Дополнительные параметры}

\begin{itemize}
    \item вложенные данные: метаданные вложений;
    \item связанная коллекция: категории;
    \item индексируемый запрос: поиск по категории и дате создания;
    \item аналитический запрос: среднее количество изменений объекта по состояниям;
    \item изменение структуры: замена вложенных категорий ссылками на отдельную коллекцию.
\end{itemize}

\subsection*{Требования к программе}

\begin{enumerate}
    \item Перенести основные объекты в назначенную документоориентированную систему, сохранив CRUD API первой лабораторной.
    \item Реализовать назначенные вложенные данные и связанную коллекцию.
    \item Добавить фильтрацию, сортировку, пагинацию и поиск по вложенным полям.
    \item Использовать ревизии \texttt{\_rev}, обработать конфликт изменений и настроить репликацию между двумя узлами.
    \item Реализовать назначенный аналитический запрос с помощью MapReduce view.
    \item Создать Mango-индекс и исследовать индексируемый запрос через \texttt{\_explain}.
    \item Настроить \texttt{validate\_doc\_update} и выполнить повторяемую миграцию существующих документов.
    \item Сохранить key-value-хранилище первой лабораторной и использовать его для кэширования запроса к назначенной системе с TTL и инвалидацией.
\end{enumerate}

\section*{Выводы}

Пользователи, заказы и история операций остались в PostgreSQL: у них фиксированные поля, роли и связи. Избранное, корзина, сессии, токены восстановления и счётчик заявок остались в Riak KV. В CouchDB перенесён товар --- документ, у которого вместе с полями живут вложения, категории и история ревизий.

Метаданные вложения лежат массивом \texttt{attachments} внутри товара: имя файла, тип, размер, контрольная сумма, описание, порядок и дата. Отдельной базы под файлы нет, содержимое файла в документ не кладётся. Категории имеют две схемы. В первой категория вложена в товар. Во второй у товара массив \texttt{category\_ids}, а сами категории --- документы базы \texttt{categories}. Версия задаётся \texttt{APP\_VERSION}. При старте и при чтении товара документ приводится к выбранной схеме; уже совпадающий документ повторно не переписывается.

Каталог фильтруется по имени, цене, наличию, категории и дате создания, сортируется и отдаётся страницами. Фильтр категории подходит к обеим схемам: и к массиву идентификаторов, и к вложенным объектам. Составной Mango-индекс \texttt{idx\_products\_category\_created\_at} построен по категории и дате. План такого запроса снимается через \texttt{\_explain} и пишется в лог, когда выбрана одна категория и задан диапазон дат.

Каждое сохранение идёт с текущим \texttt{\_rev}. Если ревизия устарела, изменение читает документ заново и повторяет запись, не больше пяти раз. После двусторонней репликации расходящиеся ветки схлопываются по правилу первой записи: остаётся ветка с самым ранним \texttt{updated\_at}. Запись документа с известным идентификатором уходит на узел \texttt{md5(id) \% 2}; если он недоступен, запрос идёт на второй. Репликация непрерывная в обе стороны, поэтому копия догоняет запись не сразу. В CAP здесь оставлены доступность и устойчивость к разделению: сразу после записи второй узел может отдать старую версию.

Аналитика --- view \texttt{changes\_by\_state}. Map берёт поколение ревизии минус один и состояние \texttt{in\_stock} или \texttt{out\_of\_stock}, reduce \texttt{\_stats} считает сумму и число, среднее --- их отношение. Результат кэшируется в Riak в бакете \texttt{product\_analytics} на 60 секунд и сбрасывается при сохранении или удалении товара.

\texttt{validate\_doc\_update} проверяет тип документа, имя, неотрицательные цену и целое количество и форму категорий под текущую схему. Отдельных типов столбцов у CouchDB нет: документ --- JSON, ограничения живут в этой функции и в проверке входных данных приложения.

CouchDB уместен для товара: вложение, смена вложенных категорий на ссылки, ревизии и MapReduce делаются одним документом. Для пользователей и заказов он не нужен: там связи и выборки, которые уже закрывает PostgreSQL. Репликация двух независимых узлов даёт копию и переживает остановку одного узла, но не даёт чтения своей последней записи на любом узле без отдельного разрешения веток. Для этого приложения CouchDB --- хранилище каталога рядом с PostgreSQL и Riak, а не замена им.
